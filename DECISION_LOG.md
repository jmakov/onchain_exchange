# Decision log

## API
| decision            | alternatives     | rationale / trade off                                                                                                                                                                                                                                                  |
|---------------------|------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| protocol SBE + SOFH | SBE + Websockets | With SBE we don't need to pay the CPU cost of parsing messages. SOFH offers lowest overhead and lowest latency. Schema evolution for SBE is available via the XML template, breaking changes are also not a problem since we just publish a new version of the schema. |

## Gateway
| decision                                                     | alternatives                     | rationale / trade off                                                                                                                                   |
|--------------------------------------------------------------|----------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| as much work as possible before reaching the matching engine | doing risk, accounting in the ME | For performance reasons we want to have in the matching engine minimum work. Offloading e.g. accounting can be solved with reservations in the gateway. |
                                                                                                                                                |

## Matching engine (ME)
| decision                                                           | alternatives                                                                                                                       | rationale / trade off                                                                                                                                                                                                                                                                                                            |
|--------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| market partition per NIC RX queue                                  | dedicated NIC RX queue per market                                                                                                  | For min. latency we could make gateway send orders only to dedicated NIC queue form which the ME process would read. But the numbert of available dedicated queues on a NIC is limited. Instead we could use this for hot markets, otherwise we'd partition multiple markets together so 1 ME process can handle multipl markets. |
| predictive tail latency at reduced performance                     | array lookup (max performance) but occasional latency spike when rebalancing the order book                                        | We could get a higher performance for the order book by using array or vectors (e.g. the QuantCup winner), but we'd be constrained by memory. Instead we're using here a data struc supporting sparese order books. If occasional latency peaks would be accepted, we could mix both - HybridBook with occasional rebalancing.   |
| no global ordering, PTP + HW timestamping for trade fairness in ME | Timestamping in the gateway using [White Rabbit swticthes for sub ns timestamp precision](https://ohwr.org/projects/wr-switch-hw/) | We could do timestamping of arriving orders in the GW, then order the stream and propagate to the ME. This would introduce additional latency. So instead ignore the problem of internal sevices having variable latency to the ME, and just rely that the ME processes whatever comes first, meaning an order arriving at T1 at GW1 could be processed sooner in the ME than another order arriving at T2 at GW2, where T2 < T1, because internal latencies might be different. What we can do is reduce it and control it |
